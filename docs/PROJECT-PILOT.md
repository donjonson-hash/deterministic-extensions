# Работа с проектом — пилот 0.2.0

Цель: проверить одну связанную правку нескольких файлов целиком, сохранив исходный проект. Runtime не использует LLM, ключи API или платные сервисы. Это локальная страница браузера с Node.js-компонентом, а не установленное расширение с доступом к диску. Адаптеры ChatGPT/Claude/Gemini пока не реализованы.

## Попробовать без своего проекта

Установите Node.js 24.15+ и Git. Из корня репозитория или распакованного `project-pilot-0.2.0.zip`:

```bash
node scripts/project-demo.mjs
```

Откройте ссылку из терминала. Три изменения уже подготовлены: настройки, модуль и тест. Просмотрите файлы → запустите проверки → создайте ветку → отмените → восстановите. Текущие файлы демо-проекта останутся прежними. Адрес демо-проекта выводится в терминале; после остановки он сохраняется, временная копия проверок удаляется. Ctrl+C завершает сервер.

## Свой проект

Поддерживается корень локального Git-репозитория с начальным коммитом и чистыми рабочими файлами/index. Сохраните текущую работу обычным способом перед запуском. Невключённые в Git файлы должны быть явно игнорируемыми или находиться вне проекта.

```bash
node scripts/project-server.mjs --project /absolute/path/to/project
```

Для проверок создайте JSON **вне целевого репозитория**:

```json
[{"name":"Node tests","argv":["node","--test"]}]
```

```bash
node scripts/project-server.mjs --project /absolute/path/to/project --checks /absolute/path/to/checks.json
```

Команды выбираются при запуске; через браузер нельзя заменить их. Проверки исполняются с правами вашей учётной записи в временной копии. **Эта копия не является защитной песочницей:** запускайте только доверенные команды и код. Проверки могут обращаться к сети, окружению и другим папкам; сам инструмент не отправляет код наружу. Зависимости и ignored/untracked файлы не копируются. В первом пилоте используйте проверки, которым достаточно tracked-файлов и уже доступных системных инструментов.

## Формат задачи

Загрузите JSON либо заполните шаблон в интерфейсе. `baseCommit` скопируйте из текущей сессии. Для каждого нового предложения нужен новый `id`.

```json
{
  "schemaVersion": 1,
  "id": "task-1",
  "title": "Обновить заголовок и убрать старую страницу",
  "baseCommit": "FULL_COMMIT_SHA_FROM_SESSION",
  "changes": [
    {"path":"src/title.txt","operation":"write","text":"New title\n"},
    {"path":"old-page.txt","operation":"delete"}
  ]
}
```

`write` задаёт полный новый текст, включая нужные переводы строк, а не фрагмент для вставки. Удаляемый файл должен существовать. Пилот проверяет схему, пути, UTF-8 и исходное состояние. Он не определяет намерение автора и не гарантирует правильность программы без подходящих тестов. Проверка синтаксиса зависит от выбранной команды; встроенного универсального анализатора языков нет.

## Что означает применение

- «Создать ветку» создаёт локальную `deterministic/<digest>` и один коммит для всего набора. Текущая ветка, index и рабочие файлы не переключаются и не заменяются. Push отсутствует.
- Все настроенные проверки должны пройти. Без настроенных проверок доступна публикация с явным сообщением об их отсутствии.
- Undo удаляет только созданную ссылку на ветку при совпадении ожидаемого коммита; открытая в worktree или изменённая ветка блокирует отмену. Это не откат произвольных действий команд проверок.
- Redo восстанавливает тот же коммит при сохранении исходного состояния и отсутствии конфликтующей ветки.
- Перезапуск не удаляет опубликованную ветку, но история Undo/Redo текущей сессии теряется. Уже созданная ветка не перезаписывается новой сессией.
- Для нового набора после публикации откройте новую сессию. Параллельная вкладка со старым digest не может применить незнакомый ей набор.

## Границы и воспроизводимость

Политика `project-branch-v1`, схема предложения `1`. Максимум 1 000 tracked-файлов и 20 MiB содержимого; HTTP-предложение максимум 2 MiB. Редактирование и удаление — только строгий UTF-8 без NUL; неизменённые бинарные файлы сохраняются. Ссылки, submodule, неоднозначные пути/регистр и переход файл↔каталог отклоняются. Рабочие байты должны совпадать с Git blobs: checkout с преобразованием CRLF или фильтрами может быть отклонён даже при чистом `git status`.

Проверки: до 8 команд, каждая до 30 секунд, вывод ограничен 64 KiB. Проверки не должны менять проверяемые файлы или создавать дополнительные файлы; такой результат блокируется. Произвольные тестовые программы сами могут быть недетерминированными — повторяемость их результата инструмент не обещает.

Digest включает исходный снимок, версию политики, ID, название и упорядоченные изменения. Git-коммит использует фиксированную служебную личность и время базового коммита. При одинаковом Git-формате и входных данных дерево и коммит воспроизводятся. Случайный ключ HTTP-сессии и временные пути относятся к адаптеру ввода-вывода и не входят в digest.

Атомарна операция создания/удаления Git ref с ожидаемым SHA. Весь файловый каталог не является транзакцией. Проверка исходника выполняется повторно перед публикацией; внешние процессы не блокируются глобально. Пилот не предназначен для конкурентного редактирования репозитория во время применения.

Сервер слушает только 127.0.0.1, требует ключ сессии, проверяет Host/Origin, не разрешает внешние скрипты. Ключ удаляется из адреса страницы и хранится в памяти вкладки. После перезагрузки откройте полную ссылку из терминала заново. Не публикуйте эту ссылку.

## Проверка разработки

```bash
npm ci --ignore-scripts
npm run verify
npx playwright install chromium
npm run test:project-browser
```

Последняя команда проверяет реальный браузерный цикл с отдельным демонстрационным Git-проектом. Установленный MV3-пример проверяется отдельно через `REQUIRE_EXTENSION=1 npm run test:browser`.
